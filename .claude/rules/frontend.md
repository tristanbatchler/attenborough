# Frontend (web/)

- SvelteKit 2 + Svelte 5 (runes), TypeScript, `@sveltejs/adapter-node`. SvelteKit config lives in `web/vite.config.ts` (the `sveltekit()` plugin); there is no `svelte.config.js`. Read `web/README.md` first.
- **The API client is generated; never hand-write API calls.** All endpoints, parameters and types come from `web/src/lib/client/`, generated by `@hey-api/openapi-ts` from `api/src/openapi.json`. No hand-written `fetch` to the API, no copied types, never edit `src/lib/client/`. After any API change: restart the API (it rewrites the spec), run `mise run web-gen-types` (or `npm run gen-types` in `web/`), and commit the regenerated client with the API change. ESLint rejects hand-written calls (`API_BY_HAND` in `web/eslint.config.js`); run the `generated-api-client` skill after frontend changes for what lint can't see. If a generated name is ugly, fix the operation ID in the API (`main.py:_operation_id`, `Router` route names), not the client.
- Call the API only from server `load` functions (`+page.server.ts`), spreading in `apiOptions(fetch)` and passing each result through `unwrap` (both in `$lib/server/api`). `unwrap` maps an unreachable API to 503, a 422 to 400 (with a message for the caller's input) and other failures to 502; don't hand-roll that per page. API settings the frontend needs (page size and so on) come from `GET /exhibit/meta` (`metaGetMeta`), never from constants duplicated in `web/`.
- Styling: semantic HTML plus the global `src/app.scss` (Pico CSS via Sass, classless, `$semantic-root-element: 'body > div'` because of SvelteKit's wrapper in `app.html`). No utility classes, no Tailwind, no component library. Use component `<style>` only for genuinely self-contained components.
- Internal links and form actions use `resolve()` from `$app/paths` (enforced by `svelte/no-navigation-without-resolve`), including query strings: ``resolve(`/ip/[address]?page=${n}`, { address })``.
- Keep server-only configuration in `$lib/server/` and `$env/dynamic/private`, never in browser bundles. Validate required configuration at startup in `init` (`src/hooks.server.ts`), not on first use. `vite build` doesn't run `init`, so builds don't need runtime settings.
- Sass: `quietDeps: true` (in `vite.config.ts`) silences deprecation warnings from third-party stylesheets such as Pico only; warnings about our own SCSS still show and must be fixed.
- Preserve the distinction between public exhibit data and authenticated/admin data.
- Captured request data (IPs, paths, credentials, user agents, headers) is shown in full, as text only: plain `{…}` expressions, never `{@html}`.
- Reuse the shared pieces rather than re-creating them: `paging(url, api)` from `$lib/server/paging` for `?page=` (validated against `/exhibit/meta`), and `ActivityTable` and `Pagination` from `$lib/components`. `Pagination`'s `href` returns `ResolvedPathname`, so callers must pass `resolve()`d links. Typing a prop or return value as `ResolvedPathname` is how to satisfy `svelte/no-navigation-without-resolve` in shared components; never disable the rule.
- Handle loading, empty, error and pagination states for exhibit timelines and summaries. Times are UTC and labelled as such (`$lib/format.ts`).
- Avoid adding dependencies or a new state-management or design system for a small change. When adding one, pin exact versions where the project's docs ask for it (hey-api does).
- Code style, as for the API: no magic or repeated strings (module-level `const`s such as `PAGE_PARAM` in `$lib/params`, or a small helper such as `pageHref`, instead of repeating a literal or an expression; scan with `mise run web-magic-strings` and judge with the `magic-strings` skill); no magic numbers (a lint error; HTTP statuses from `node:http2`'s `constants`); no pointless type annotations where inference already gives the type; explicit types at boundaries (props via `PageProps`/`LayoutProps`, load functions via `./$types`).
- Checklist after any frontend change: `mise run fix`, then `mise run check` from the repo root (it runs `npm run check`, `lint`, `format:check` and `build` in `web/`). The same checks exist as npm scripts, named as in the user's other project, stashit: `check` (svelte-check with `--fail-on-warnings`), `lint`/`lint:fix` (ESLint with typescript-eslint `strictTypeChecked` + `stylisticTypeChecked`), `format`/`format:check` (Prettier) and `gen-types`. TypeScript is stricter than `strict` (see `tsconfig.json`). `exactOptionalPropertyTypes` is off only because the generated client fails it, and svelte-check can't exclude imported files. For behaviour, run the built server (`node build`) against the real API and check the pages with curl. There's no headless browser here: say so, and don't claim you checked visual appearance.
- Generated code (`src/lib/client/`) is excluded from ESLint and Prettier; never lint-fix or format it by hand. Don't loosen a lint rule to get code through; fix the code (e.g. `String(n)` in template literals under `restrict-template-expressions`).
- Research before assuming: check SvelteKit, Pico and hey-api behaviour in their docs or the installed sources (`node_modules`), since versions move quickly.
