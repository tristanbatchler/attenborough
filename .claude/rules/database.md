# PostgreSQL and sqlc

- Inspect `schema.sql`, `queries.sql`, sqlc configuration, generated output, and call sites together before changing persistence.
- Treat SQL/schema/query sources as authoritative. Never hand-edit generated sqlc files such as `models.py`, `enums.py`, or `queries.py`.
- After changing source SQL or schema, regenerate with `mise run sqlc` (or `uv run sqlc generate --file src/attenborough/db/sqlc.yaml` from `api/`) and inspect the generated diff, ignoring whitespace (`git diff -w`). Generated files are not ruff-formatted, so formatting-only churn is expected.
- The schema is described twice and kept equal: `migrations/` (numbered plain-SQL files, `0001_baseline.sql`, `0002_...`, applied in order; how every production database is built and changed, keeping its data) and `schema.sql` (the complete current schema: what sqlc reads, and what a development reset applies). `src/tests/test_migrations.py` (in `mise run check`, needs the development database) builds both in scratch schemas inside a rolled-back transaction and fails on any difference in tables, columns (position included: generated rows are positional), constraints, indexes, functions, triggers, sequences or enums. The user chose migrations (option (c), `docs/plan-first-field-season.md`) once the honeypot's data had to be kept.
- `db/schema.py` owns both: `migrate` applies pending migrations, each in its own transaction with its `schema_migrations` row (version, name, SHA-256); `reset_schema` (development only) drops `public`, applies `schema.sql` and records every migration, in one transaction. Startup (`main.py:_ensure_current_schema`) refuses to serve unless the database is current: on a `/dev/tty` it offers to migrate (pending) or reset (missing, diverged); with no terminal it refuses and logs what to run. Production runs as an app role that can't change the schema; migrations there run as the owner role (`docker compose run --rm migrate`, `deploy/README.md`).
- Every query, including the migration bookkeeping, the reset and the development seed, lives in `queries.sql` and is called through the generated `queries.py`. The only raw SQL is executing `schema.sql` and the migration files, and the catalog query in `test_migrations.py`. PostgreSQL can't take identifiers (such as a database name) as parameters, which is why a reset replaces the `public` schema instead of dropping the database.
- A closed set of values stored in the database (router groups, event kinds, decoy types) is a PostgreSQL enum in `schema.sql`, and the API uses the enum sqlc generates from it (`db.enums`), never a hand-written copy. Then `schema.sql` is the only definition, and a literal in SQL, such as `'honeypot'` in `ListRecentEvents`, is checked by PostgreSQL against the type.
- Keep `schema.sql` and migrations plain DDL that sqlc can parse. No `DO $$` blocks: sqlc can't see types created inside them, and the generated enums silently become `typing.Any` (proven experimentally; PostgreSQL 18 has no `CREATE TYPE IF NOT EXISTS`). A trigger's `CREATE FUNCTION ... AS $$ ... $$` is fine. Use `IF NOT EXISTS` only for extensions. Keep the `schema_migrations` table. Don't grant to role names in a migration: the owner's default privileges (`deploy/database.sql`) cover every table it creates.
- Changed only `queries.sql` → regenerate; data is kept. Changed the schema → change `schema.sql` and add the next migration making the same change (a new column goes last in `schema.sql` too), regenerate, then `scripts/migrate.py` (or reset the development database). Never edit a migration that a database you keep has applied, and never reset production.
- The exhibit's listings are keyset-paged (`ListRecentEvents`, `ListIpEvents`): one sub-select per event table, each reading its `(time, id)` index with its own `LIMIT`. Don't fold them into a `UNION ALL` view: measured on two million rows, the planner then read and sorted a whole table (2 s). Per-address totals (`ip_activity`) are kept by insert triggers, not counted per request; anything that ever deletes events must recompute them. Check query plans against a seeded database (`scripts/seed_db.py`) before changing exhibit queries.
- `path_category(path)` (`schema.sql`) is the one definition of what a path was after: an `IMMUTABLE` SQL function returning the `path_category` enum, never stored, so a rule change (a new migration, `CREATE OR REPLACE FUNCTION`) recategorises all past requests. `src/tests/test_path_categories.py` checks it on real paths. In an aggregate, run it once per distinct path (a `MATERIALIZED` CTE, as in `CountCategoriesSince`): the planner otherwise runs it on every joined row.
- The Patterns page's queries (`queries.sql`, "The Patterns page") read all-time figures only from the per-address running totals (`ip_activity`, `ip_request_paths`, `ip_locations`), and figures over requests or login attempts only `since` a time, through the time indexes. Keep new aggregates to one of the two: a full scan of `telemetry_hits` took seconds on two million rows.
- Preserve constraints, indexes, transaction semantics, timestamp meaning/time zone handling, and IP address types.
- Use parameterised queries. Never interpolate request data into SQL strings.
- Consider concurrency, uniqueness, retention, pagination, and query plans for event ingestion and exhibit queries.
- Resetting the development database (`attenborough_dev`) is approved. Never reset, alter or delete data in any other database (the production `attenborough` included) without the user's explicit approval for that database. The development database lives on the same PostgreSQL server as production.
- Before changing what a column or event *means* (not just its shape), explain the effect on existing data and on the exhibit, and ask.
